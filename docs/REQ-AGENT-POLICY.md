## 1. Scope

This document specifies the hard functional, non-functional, and regulatory requirements for the Agent Policy Engine — a declarative, YAML-driven governance system that governs AI agent behaviour across all 24 opencode hook types. It replaces the current shell-scripted, regex-array-based `rules`/`hooks` tooling with a unified policy DSL, CLI management interface, and profile system.

The policy engine provides:
- **Event → Match → Action** declarative policy definition in YAML
- **YAML → JSON policy rendering** via `yq` — zero Python, shell-first pipeline
- **Static plugin JS** — written once, tested once, never regenerated; loads `policies.json` at runtime
- **Per-hook-type management CLIs** — `rules`, `guards`, `tool-guards`, etc.
- **Policy lifecycle** — validate, dry-run, render, apply, audit
- **Named profiles** — save/load/switch policy bundles
- **Full audit trail** — tamper-evident logging of every policy decision
- **Compliance evidence** — structured logs meeting EU AI Act Art. 12, ISO 42001, and A2A governance requirements

**Out of scope:**
- Runtime policy enforcement engine (the static plugin evaluates policies at runtime via opencode's hook pipeline)
- LLM-based policy evaluation (Phase 2, referenced from V2 REQ-HOOKS-050-057)
- A2A Server endpoint hosting (covered by REQUIREMENTS-A2A.md)
- Containerized agent isolation policy (covered by REQ-AGENT-CONTAINERS.md)
- MCP protocol governance (separate requirement track)

## 2.1 Artifact Persistence and Template Seeding

The system follows the same template→userfile→deploy pattern as the current `rules` command:

| Layer | Location | Git | Purpose |
|-------|----------|-----|---------|
| **Templates** | `workspace/config/opencode/policies/template/*.template.yaml` | Tracked | Immutable source of truth. Default rules and guards. Copied to user location on first use. |
| **Userfiles** | `workspace/config/opencode/policies/*.yaml` | **Gitignored** | User's working copies. Edited by CLI commands (`rules add`, `guards delete`, etc.). Never committed. |
| **Rendered JSON** | `workspace/config/opencode/plugins/policies.json` | **Gitignored** | Generated by `yq` from userfiles at render time. Never committed. |
| **Runtime deploy** | `~/.config/opencode/plugins/` (both files) | N/A | Where opencode loads from. Copied by `policy apply`. |
| **Audit trail** | `~/.config/opencode/logs/policy-decisions.jsonl` | N/A | Written by the static plugin at runtime. Never committed. |

**Template Seeding (FR-2.4):** On first use of any domain CLI, the system SHALL check if the userfile exists. If absent, copy the corresponding template to the userfile location. This mirrors the current `_init_userfile` pattern. After seeding, the userfile is the editable working copy; the template is never modified.

**Profile Storage:** Profiles are stored in `workspace/config/opencode/policies/profiles/`. User-created profiles MAY be committed for team sharing; built-in template profiles (`standard.template.yaml`, `strict.template.yaml`) are tracked in the template directory.

## 2. Terminology

| Term | Definition |
|------|------------|
| **Policy** | A single Event → Match → Action rule expressed in YAML. Maps one opencode hook event to conditional matching and prescribed action. |
| **Policy File** | A YAML file (`rules.yaml`, `guards.yaml`, `tool-guards.yaml`, etc.) containing an array of policies targeting a specific hook domain. |
| **Policy Engine** | The bash + `yq` pipeline that validates YAML policies and renders them into `policies.json`, deployed alongside a static plugin JS file. |
| **Hook Event** | An opencode lifecycle event (e.g., `chat.messages.transform`, `tool.execute.before`) that a policy attaches to. One of the 24 hook types. |
| **Match Condition** | A `field operator value` triple that filters when a policy fires (AND logic by default, OR via `match_groups`). |
| **Action** | The prescribed outcome when conditions match: `inject` (system prompt), `block`, `allow`, `warn`, `ask`, `modify`, `env`, `run`. |
| **Profile** | A named, versioned collection of policy references that can be activated as a unit. Stored as YAML in `profiles/`. |
| **Dry Run** | Simulated evaluation of a policy against test input without deploying the plugin. |
| **Policy Validation** | Schema check + hook event compatibility verification before rendering. |
| **Policy Render** | Convert enabled YAML policies from all domain files into `policies.json` via `yq`. No code generation — the plugin JS is static. |
| **Policy Apply** | Render `policies.json` + copy the static plugin JS → `~/.config/opencode/plugins/`. |
| **Audit Trail** | Append-only, tamper-evident JSONL log of every policy evaluation decision, with structured metadata. |

## 3. Functional Requirements

### FR-1: Declarative Policy Definition

**FR-1.1 — YAML Policy DSL:**
The system SHALL support policy definition in YAML with a schema covering all 24 opencode hook types. A policy SHALL consist of: unique name, optional description, enabled flag, hook event, optional scope, priority, optional agent filter, match conditions, and action block.

**FR-1.2 — Event → Match → Action Structure:**
Every policy SHALL follow the universal `Event → Match → Action` structure observed across industry policy engines (Anthropic Constitutional Classifiers++, Google Agent Gateway + Project Mariner, AWS Bedrock Guardrails, NVIDIA NeMo Guardrails Colang DSL, AgentSpec/ShieldAgent academic frameworks, Hooksmith, Zrb).

**FR-1.3 — Multiline System Prompt Injection:**
For `inject` actions, the system SHALL support multi-line system prompt text with full markdown formatting, preserving whitespace and indentation.

**FR-1.4 — Regex with Flags:**
Match conditions with `operator: regex` SHALL support standard regex flags (`i`, `m`, `s`, `g`) specified in a `flags` field.

**FR-1.5 — Compound Conditions:**
The system SHALL support AND logic via the `match` array (all conditions must match) and OR-of-ANDs logic via `match_groups` (any group fully matching triggers the policy).

**FR-1.6 — Agent-Scoped Policies:**
Policies SHALL support an optional `agent` field to restrict policy application to specific agent identities. Wildcard `"*"` is the default (all agents).

**FR-1.7 — Priority Ordering:**
Policies SHALL support a `priority` integer field (default 0). Higher priority policies evaluate first. Within equal priority, declaration order is preserved.

**FR-1.8 — Enable/Disable Without Deletion:**
Every policy SHALL support an `enabled` boolean field. Disabled policies are skipped during rendering but retained in the source file.

**FR-1.9 — Executable Policy Actions (`run`):**
The system SHALL support `action: run` which executes an external script via Bun's built-in `$` shell API (not a system shell — Bun auto-escapes arguments, preventing command injection). The script receives the full event context as JSON on stdin and MUST return a decision object as JSON on stdout. Supported decisions: `block` (throw, kill execution), `allow` (proceed normally), `warn` (inject reason into system prompt, proceed), `modify` (deep-merge `fields` into tool arguments). Script execution SHALL be time-bounded with a configurable timeout (default 5000ms). The run action SHALL be compatible with `tool.execute.before`, `tool.execute.after`, and `command.execute.before` hook events, matching the event-action compatibility matrix defined in the specification.

**FR-1.10 — Run Action stdin/stdout JSON Protocol:**
The run action SHALL follow a well-defined stdin/stdout JSON protocol. stdin SHALL contain a JSON object with context fields keyed by hook event: `hook` (event name), `tool` (tool identifier), `sessionID`, `callID`, `args` (tool arguments), and `result` (for `tool.execute.after` only). stdout SHALL contain a single JSON object with `action` (one of `block`/`allow`/`warn`/`modify`), `reason` (optional, for block/warn), and `fields` (optional, for modify — merged into output args). Every non-success condition (non-zero exit, timeout, empty stdout, invalid JSON, unknown action, script not found) SHALL be treated as `block` (fail-closed). There SHALL be NO path to `allow` by default — the script MUST explicitly return `{"action":"allow"}`.

**FR-1.11 — Run Action Audit Trail:**
Every `run` action decision SHALL be logged to the structured audit trail with: action type (`"run"`), full script path, process exit code, wall-clock execution time (ms), the parsed decision object, and SHA-256 hash of raw stdout for tamper evidence. The logged decision SHALL be searchable by policy name and session ID.

### FR-2: Policy File Architecture

**FR-2.1 — Separate Files Per Hook Domain:**
Policies SHALL be organized into domain-specific YAML files. Templates are the tracked source of truth; userfiles are gitignored working copies:
| Template (tracked) | Userfile (gitignored) | Hook Domain | CLI Command |
|------|------|-------------|-------------|
| `template/rules.template.yaml` | `rules.yaml` | `chat.messages.transform` (user-message scope) | `rules` |
| `template/guards.template.yaml` | `guards.yaml` | `chat.messages.transform` (assistant-message scope) | `guards` |
| `template/tool-guards.template.yaml` | `tool-guards.yaml` | `tool.execute.before`, `tool.execute.after` | `tool-guards` |
| `template/shell-guards.template.yaml` | `shell-guards.yaml` | `shell.env`, `tool.execute.before` (shell scope) | `shell-guards` |
| `template/system-rules.template.yaml` | `system-rules.yaml` | `experimental.chat.system.transform` | `system-rules` |

**FR-2.2 — Extensible File Registry:**
Adding a new policy domain SHALL require: a new template YAML file, a new CLI script (~30 lines sourcing shared library), and a manifest registration. No modification to existing files.

**FR-2.3 — Config Path Resolution:**
Policy file paths SHALL resolve via override chain (highest to lowest): `POLICY_DIR` env var → `policies.dir` in automation config → default `workspace/config/opencode/policies/`.

**FR-2.4 — Template Seeding on First Use:**
On first invocation of any domain CLI, the system SHALL copy the corresponding template YAML to the userfile location if the userfile does not already exist. This mirrors the current `_init_userfile` pattern. The template SHALL never be modified by any CLI command.

**FR-2.5 — Gitignore Boundary:**
All userfiles (`*.yaml` directly in `policies/`), rendered `policies.json`, and user profiles SHALL be gitignored. Templates (`template/*.template.yaml`) and built-in profile templates are the only tracked policy files.

### FR-3: Policy Rendering

**FR-3.1 — YAML → JSON Conversion via yq:**
`policy render` SHALL merge all enabled policies from all userfile YAMLs in the policy directory into a single `policies.json` file via `yq`. Templates are the seed; userfiles are the editable source. No Python VM, no code generation, no runtime JS manipulation.

**FR-3.2 — Static Plugin JS Architecture:**
The opencode plugin (`add-user-message-context.js`) SHALL be a static file in `workspace/config/opencode/plugins/` — written once, tested once, version-controlled, never regenerated. At runtime, it loads `policies.json` from its own directory via `fs.readFileSync` and evaluates all policy match conditions and actions. The plugin handles all 24 opencode hook types.

**FR-3.3 — Deploy Artifacts:**
`policy apply` SHALL deploy exactly two files to `~/.config/opencode/plugins/`:
1. The static plugin JS file (copied verbatim from `workspace/config/opencode/plugins/`)
2. `policies.json` (rendered from userfile YAMLs, staged alongside the static JS)

**FR-3.4 — Deployment Flow:**
`policy apply` SHALL: (1) run `policy render` (userfile YAMLs → policies.json via yq), (2) copy the static plugin JS + `policies.json` to `~/.config/opencode/plugins/`, (3) display which policies are active and a reminder to restart opencode sessions.

**FR-3.5 — Template Immutability:**
Template files (`template/*.template.yaml`) SHALL remain immutable. Only userfiles are edited by CLI commands. The rendered `policies.json` is disposable — regenerated from userfiles on every `policy render`.

### FR-4: CLI Commands

**FR-4.1 — Domain-Specific CLIs:**
Each policy domain SHALL have a dedicated CLI command as a thin shell wrapper sourcing a shared library (`lib/context.sh`). Each supports: `list`, `add -r REGEX -t TEXT`, `delete NAME`, `update NAME -r REGEX -t TEXT`, `enable NAME`, `disable NAME`.

**FR-4.2 — Named Policy References (Not Array Indices):**
Policy management SHALL reference policies by their unique `name` field, not by numeric array index. `rules delete no-speculation`, not `rules delete 3`.

**FR-4.3 — Policy Lifecycle CLI:**
`policy` command SHALL provide: `validate` (schema + compat check), `render` (YAML → policies.json via yq), `apply` (render + deploy), `list` (all policies across all files), `show NAME` (full details), `dry-run NAME -i INPUT` (simulate).

**FR-4.4 — Profile CLI:**
`profile` command SHALL provide: `list`, `show NAME`, `apply NAME` (activate profile), `save NAME -i FILES...` (snapshot current policies as profile), `delete NAME`.

**FR-4.5 — Extension Manifest Registration:**
Each CLI command SHALL be registered in `extension.manifest.yaml` with binary path, description, features list, health check, and banner priority.

### FR-5: Profiles

**FR-5.1 — Profile Structure:**
A profile SHALL be a YAML file containing: `name`, `version`, `description`, and `policies` (a list of policy file references with optional per-policy enable/disable overrides). Profiles are stored in `profiles/`.

**FR-5.2 — Profile Activation:**
`profile apply NAME` SHALL: (1) validate the profile, (2) render policies.json from the profile's policy set (with per-policy overrides applied), (3) deploy the static plugin JS + policies.json.

**FR-5.3 — Profile Inheritance:**
Profiles SHALL support `extends` to compose from a base profile. Override semantics: same policy name overrides, new names are appended.

**FR-5.4 — Profile Portability:**
Profiles SHALL be portable YAML files suitable for git versioning and sharing. No absolute paths or machine-specific data.

**FR-5.5 — Built-in Profile Templates:**
The system SHALL ship with default profiles: `standard` (balanced defaults), `strict` (full enforcement), `lenient` (baseline context only), `code-review` (review-focused rules).

### FR-6: Validation and Testing

**FR-6.1 — Schema Validation:**
`policy validate` SHALL validate all policy YAML files against the schema. Validation errors SHALL report: file path, policy name, field, expected type/value, actual value.

**FR-6.2 — Hook Event Compatibility:**
Validation SHALL verify that each policy's declared hook event maps to a valid opencode hook type and that the action type is compatible with the event (e.g., `block` is valid for `tool.execute.before` but not for `shell.env`).

**FR-6.3 — Dry Run:**
`policy dry-run NAME -i 'JSON_INPUT'` SHALL simulate policy evaluation: parse the input, evaluate match conditions, and report whether the policy would trigger, with which action.

**FR-6.4 — Conflict Detection:**
Validation SHOULD detect conflicting policies (same event, overlapping match conditions, contradictory actions) and warn at render time. Conflicts SHALL NOT block rendering (warn, don't block).

### FR-7: Observability and Audit

**FR-7.1 — Policy Decision Audit Trail:**
The deployed static plugin SHALL log every policy evaluation decision to a structured JSONL audit file at `~/.config/opencode/logs/policy-decisions.jsonl`. Each entry SHALL include: timestamp, policy name, hook event, match result, action taken, agent ID, session ID, input hash.

**FR-7.2 — Audit Entry Schema:**
Audit entries SHALL follow the AgentContract-compatible format:
```json
{
  "timestamp": "ISO 8601",
  "run_id": "UUID v4 — session ID",
  "policy_name": "string",
  "event": "hook event name",
  "match": true | false,
  "action": "inject | block | allow | warn | ask | modify | env | run",
  "action_detail": "action-specific payload (hash for non-run actions, structured JSON string for run actions)",
  "agent": "agent identifier",
  "delegation_depth": 0,
  "parent_sessionID": "null | session UUID",
  "input_hash": "SHA-256 of matched input"
}
```
For `action: run` entries, `action_detail` SHALL be a JSON object encoded as string containing: `script_path` (full path to executed script), `exit_code` (process exit code), `wall_time_ms` (execution duration), `decision` (the parsed decision object from stdout), and `stdout_hash` (SHA-256 of raw stdout for tamper evidence).

**FR-7.2a — Subagent Delegation Tracking:**
When a policy fires during a subagent's tool execution (spawned via the `task` tool), the audit entry SHALL record `delegation_depth` (integer, 0 for parent session, 1+ for nested subagents) and `parent_sessionID` (the session that spawned this subagent, or null for the root session). This enables reconstruction of multi-agent delegation chains for A2A trust model compliance (REG-5.3) and incident forensics.

**FR-7.3 — Tamper Evidence:**
Audit entries SHALL form a hash chain (each entry includes `prev_hash` of the previous entry) per-session. The final entry's hash SHALL be logged to `session_audit_chain` for post-hoc verification.

**FR-7.4 — Audit Log Retention:**
Audit logs SHALL be retained for a minimum of 6 months (EU AI Act Art. 12 + Art. 26(6)). Retention SHALL be configurable.

**FR-7.5 — Policy Decision Explanation:**
When a `block` or `ask` action fires, the system SHALL surface: the policy name, the matched condition, and the action reason to both the operator (stderr/log) and the agent (via `permission.decision_reason`).

### FR-8: Policy Pack Management

**FR-8.1 — Pack Installation:**
`profile install SOURCE` SHALL install policy packs from: local file path, git repository URL, or well-known registry (future). Installed packs appear in `profiles/`.

**FR-8.2 — Pack Updates:**
`profile update NAME` SHALL pull updates for git-installed packs, respecting local overrides.

**FR-8.3 — Pack Removal:**
`profile remove NAME` SHALL delete the profile file and its associated deployment state.

## 4. Non-Functional Requirements

### NFR-1: Performance

**NFR-1.1 — Policy Render Speed:**
`policy render` (yq YAML → JSON conversion) SHALL complete in under 200ms for up to 100 policies.

**NFR-1.2 — Plugin Evaluation Overhead:**
The deployed static plugin's per-message policy evaluation SHALL complete in under 1ms for up to 50 policies (measured at the `experimental.chat.messages.transform` hook level).

**NFR-1.3 — CLI Responsiveness:**
All CLI commands (`list`, `add`, `delete`, etc.) SHALL complete in under 200ms for up to 100 policies.

### NFR-2: Security

**NFR-2.1 — Fail-Closed on Render Error:**
If `policy render` encounters any unrecoverable error (malformed YAML, invalid regex, incompatible event-action pair), it SHALL fail with exit code 1 and NOT produce a partial output file.

**NFR-2.2 — No Credentials in Policy Files:**
Policy YAML files SHALL NOT contain credentials, API keys, or secrets. Environment variable references (`$env:VAR`) SHALL be the only mechanism for secret injection.

**NFR-2.3 — Audit File Permissions:**
Audit log files SHALL be created with mode 0600 (owner read/write only).

**NFR-2.4 — Input Sanitization:**
Match condition values from user input (regex patterns, field names) SHALL be validated before insertion into the policy YAML. User-provided regex SHALL be tested for compile validity. `yq` handles JSON-safe output escaping.

**NFR-2.5 — Deny-by-Default Principle:**
The deployed static plugin SHALL default to denying tool calls that match no explicit allow policy (fail-closed for tool execution hooks).

**NFR-2.6 — Run Action Fail-Closed:**
If a run action script exits with non-zero status, times out, produces invalid or empty JSON on stdout, or is not found on disk, the policy engine SHALL treat the outcome as `action: block` (fail-closed). Truncated, malformed, or missing stdout output SHALL NOT result in allow-by-default. The block reason SHALL be surfaced to the user and logged to the audit trail with the specific failure cause (exit code, timeout duration, parse error message).

**NFR-2.7 — Run Action Script Trust Boundary:**
Scripts invoked by `action: run` execute with the same user identity and filesystem permissions as the opencode plugin process. Policy authors SHALL NOT include commands from untrusted sources in run action paths. The `command` field SHALL be validated at render time to confirm the script exists on disk. Run actions SHALL NOT execute arbitrary shell expressions — the `command` field is treated as a literal path, not an evaluated expression. Bun's built-in `$` shell API SHALL be the execution layer (not `/bin/sh`), which auto-escapes all arguments and prevents command injection. Every run action execution SHALL be logged to the audit trail with the full script path, process exit code, and wall-clock execution time.

### NFR-3: Reliability

**NFR-3.1 — Atomic File Operations:**
Policy file edits SHALL use write-to-temp-then-mv for atomic replacement. The existing file SHALL remain intact if an edit fails mid-operation.

**NFR-3.2 — Rollback on Failed Deploy:**
If `policy apply` succeeds at render but fails at file copy, the previous successfully deployed plugin + policies.json SHALL remain in place.

**NFR-3.3 — Concurrent Access Safety:**
The system SHALL detect if multiple processes attempt to edit the same policy file and fail with a clear message rather than corrupting state.

### NFR-4: Maintainability

**NFR-4.1 — Shared Library Architecture:**
Core functions (`_yq_query`, `_insert_policy`, `_delete_policy`, `_render_json`, `_deploy`, `_audit_log`) SHALL reside in a shared sourced library (`lib/context.sh`). Each CLI command is a thin wrapper. No Python VMs in the pipeline — `yq` is the only non-shell dependency for YAML processing.

**NFR-4.2 — New Hook Type Addition:**
Adding support for a new opencode hook type SHALL require changes to only two files: the static plugin JS file (add hook handler) and the new domain YAML file. No pipeline changes needed.

**NFR-4.3 — All Files Under 512 Lines:**
All source files (shell scripts, YAML schemas, JS templates) SHALL remain under 512 lines per AGENTS.md Rule 12.

## 5. Regulatory Requirements

### REG-1: EU AI Act Compliance

The following requirements derive from the EU AI Act, effective **2 August 2026**.

#### REG-1.1 — Automatic Logging (Article 12)

The system SHALL satisfy Article 12(1) and 12(2) through the audit trail (FR-7.1 through FR-7.4). When processing on behalf of a high-risk AI system (classified under Article 6 / Annex III), the deployed static plugin SHALL log:
- Start and end time of each policy evaluation (Art. 12(3)(a))
- The policy identity (name, version, source file) (Art. 12(3)(b))
- The input data that triggered the policy (hashed for data minimization) (Art. 12(3)(c))
- The decision outcome and any human override events (Art. 12(3)(d))
- Agent identity and session identity for attribution

Logs SHALL be retained for a minimum of 6 months per Article 26(6).

> Per WS-4 §3.1.1: "For autonomous agents, this requires continuous logging of: all tool calls, decisions, context windows used, model outputs, human override events, state transitions."

#### REG-1.2 — Human Oversight (Article 14)

For policies governing high-risk operations, the system SHALL:
- Provide clear information about the policy's identity, scope, and decision rationale (Art. 14(4)(a))
- Display block/ask decisions to the user with actionable explanation (Art. 14(4)(b)-(c))
- Support `action: ask` as a human-in-the-loop pause point before sensitive tool execution (Art. 14(4)(d))
- Enable operators to disable or override policies at session level (Art. 14(4)(e) — "stop button" equivalent)
- Log all human override events with timestamps and operator identity (Art. 14(5))

> Per WS-4 §3.1.2: "Stop button requirement: Every autonomous agent MUST have a mechanism for safe halting. This is not optional — it is a legal requirement for high-risk systems."

#### REG-1.3 — Deployer Duties (Article 26)

The system SHALL support deployer obligations by:
- Providing logs suitable for 6+ month retention with export capability (Art. 26(6))
- Enabling the deployer to suspend policy enforcement if a risk is identified — via `policy disable` (Art. 26(5))
- Ensuring input data processed by policies is relevant and limited to what is necessary for the match condition (Art. 26(4))
- Supporting the deployer in fulfilling DPIA obligations under GDPR Art. 35 using the structured audit trail (Art. 26(9))

#### REG-1.4 — High-Risk Classification Awareness (Article 6 / Annex III)

The system SHALL support classification documentation by:
- Recording the specific agent use case and Annex III category (if applicable) in audit metadata for each policy decision
- Flagging policy decisions that involve Annex III categories (employment, essential services, credit, education)
- Enabling the deployer to document the Article 6(3) derogation assessment for policies claiming non-high-risk status
- Maintaining the action inventory required for agentic system compliance assessment

> Per the May 2026 Draft Guidelines: "interconnected and agentic AI systems coordinating linked actions serving a high-risk purpose are assessed as a whole."

#### REG-1.5 — Transparency (Article 50)

The system SHALL:
- Clearly indicate to the user when a policy has modified or blocked an agent action (Art. 50(1) — AI interaction disclosure)
- Include policy provenance metadata (source file, version, author) visible to both operators and deployers
- For text-modifying policies (`action: modify`, `action: inject`), the modified/injected content SHALL be distinguishable from original agent output where technically feasible

#### REG-1.6 — Risk Management System (Article 9)

The system SHALL support the Article 9 risk management lifecycle:
- Documented risk assessment for each policy (FRIA integration point)
- Continuous monitoring via audit trail (Art. 9(2)(c))
- Risk mitigation hierarchy: design elimination (deny dangerous actions) → control measures (block/ask policies) → information and training (inject context) (Art. 9(5))
- Per-hazard and overall residual risk documentation
- Audit trail suitable for post-market monitoring (Art. 72)

#### REG-1.7 — Technical Documentation (Article 11 + Annex IV)

The system SHALL generate and maintain:
- Policy inventory with descriptions, hook events, match conditions, and actions (Annex IV §1-2)
- Policy version history and change log
- Design rationale for each policy's risk assessment (Annex IV §2)
- Performance metrics for policy evaluation (latency, match rate, false positive rate) (Annex IV §6)
- Integration documentation with opencode hook system (Annex IV §2)

### REG-2: GDPR Article 22 — Automated Decision-Making

If the policy engine is used to govern agents making automated decisions that "produce legal effects concerning [the data subject] or similarly significantly affects [them]" (GDPR Art. 22(1)):
- Policies with `action: block` or `action: deny` on tool calls SHALL include a documented human review pathway
- `action: ask` SHALL be the default action for policies governing high-stakes decisions
- The audit trail SHALL provide sufficient information for data subjects to understand the logic involved (Art. 22(3))
- The system SHALL support data subject rights: access to audit records, contestation of decisions, human intervention (Art. 22(3))

> Per the CJEU Schufa case (C-634/21): credit scoring that third parties treat as a decisive factor constitutes automated decision-making — even if a human makes the final decision. The policy engine's `ask` action SHALL ensure meaningful human involvement, not rubber-stamping.

### REG-3: ISO/IEC 42001:2023 Alignment

The policy engine SHALL support ISO/IEC 42001 alignment:
- **Clause 4 (Context):** Documented policy scope, stakeholder requirements, and regulatory obligations per policy domain
- **Clause 6 (Planning):** Each profile maps to risk assessment objectives; policy enable/disable supports risk treatment
- **Clause 7 (Support):** Audit logs provide documented information; profile YAML files are version-controlled documented information
- **Clause 8 (Operation):** Policy generation and deployment are AI system lifecycle controls
- **Clause 9 (Evaluation):** Audit trail enables monitoring, measurement, and internal audit of policy effectiveness
- **Clause 10 (Improvement):** Policy dry-run and conflict detection enable corrective action and continual improvement

### REG-4: OWASP Top 10 for LLM Applications

| OWASP Entry | Relevance | Requirement |
|-------------|-----------|-------------|
| **LLM01: Prompt Injection** | Malicious input may bypass regex-based match conditions | Match conditions SHALL be evaluated by the static plugin at runtime, not injected into system prompts before evaluation. User-provided regex patterns SHALL be validated for compile validity at render time to prevent ReDoS attacks. |
| **LLM06: Excessive Agency** | Policies govern tool execution scope | Policies SHALL default to deny-by-default for tool execution hooks. Explicit `action: allow` required for all governed tools. Least privilege principle: unknown tools are denied. |
| **LLM07: Insecure Plugin Design** | Plugin is an opencode plugin | Static plugin SHALL follow least privilege: only the hooks with policies defined in policies.json are active. No `eval()`, no dynamic code evaluation. |
| **LLM02: Sensitive Information Disclosure** | Audit logs may contain sensitive context | Audit logs SHALL hash input data, not store raw sensitive content. PII patterns in match conditions SHALL be flagged at validation time. |
| **LLM10: Unbounded Consumption** | Policy evaluation overhead | Per-message policy evaluation SHALL be bounded: max 50 policies per hook, max 5ms evaluation time per hook. |

### REG-5: A2A Protocol Governance Requirements

The policy engine SHALL support A2A governance requirements identified in REQUIREMENTS-A2A.md and the A2A Protocol Specification v1.0:

#### REG-5.1 — Pre-Action Authorization (A2A Community Consensus)

For A2A remote agent tool calls governed by policies:
- Policies SHALL be evaluated deterministically before remote agent invocation
- `action: block` SHALL prevent the remote agent call entirely
- `action: ask` SHALL pause for human approval before remote invocation
- Policy decisions for A2A calls SHALL be logged with the remote agent domain and task ID

#### REG-5.2 — Skill-Level Access Control (A2A AgentCard Mapping)

Policy `agent` field SHALL support mapping to A2A AgentCard `skills[].id` for per-skill access control on remote agents.

#### REG-5.3 — Delegation Chain Awareness (A2A Trust Model)

When Agent A invokes Agent B via A2A, and Agent B invokes Agent C:
- The policy engine's audit trail SHALL record the full delegation chain
- Policies with `agent` scope SHALL be evaluated for each agent in the chain
- Audit entries SHALL include `delegation_depth` and `parent_task_id` fields

#### REG-5.4 — Circuit Breaking (A2A Governance)

When a policy's `block` action fires repeatedly for the same A2A remote agent within a short window:
- The system SHOULD escalate to circuit-breaker state (CLOSED → OPEN)
- Circuit-breaker state SHALL be logged as a structured event
- Manual override (`profile apply`) SHALL be required to reset from OPEN state

### REG-6: DORA / NIS2 — Incident Reporting

For deployments in financial services (DORA) or critical infrastructure (NIS2):
- Policy-triggered blocks that constitute ICT incidents SHALL be flagged in the audit trail
- Incident reports SHALL support 24h early warning / 72h notification / 1-month final report timelines (NIS2 Art. 20)
- Audit trail SHALL support export in machine-readable format for incident response

### REG-7: Data Residency & Sovereignty

- Policy audit logs SHALL reside within the jurisdiction of the deployer's choosing
- Cross-jurisdictional data flows (e.g., A2A remote agent invocation to non-EU domains) SHALL be logged with jurisdiction metadata
- No policy data SHALL be transmitted to external services without explicit configuration

## 6. Constraints

| ID | Constraint | Source |
|----|------------|--------|
| C-1 | The policy engine SHALL NOT make network calls to any external policy evaluation service (deterministic, local-only evaluation). | EU AI Act Art. 9(5) — risk elimination through design; OWASP — no remote LLM calls |
| C-2 | Policy files SHALL be valid YAML 1.2 and SHALL pass schema validation before rendering. | Industry standard (all 10+ policy engines converge on YAML). |
| C-3 | The static plugin JS SHALL NOT use `eval()`, `Function()`, or dynamic code execution. Policies are loaded from JSON, not generated into code. | OWASP LLM07 — Insecure Plugin Design. |
| C-4 | No policy SHALL contain credentials, API keys, or secrets in cleartext. | AGENTS.md Rule 8 — Env Var Safety. |
| C-5 | All shell scripts SHALL use `set -euo pipefail` and pass shellcheck. | AGENTS.md — Rule 1: Never Circumvent Quality Gates. |
| C-6 | Userfiles (`*.yaml` directly in `policies/`) and rendered `policies.json` SHALL be gitignored. Only templates (`template/*.template.yaml`) are tracked. | AGENTS.md Rule 3.5 — History is immutable. User policy data is not project source. |
| C-7 | The system SHALL NOT depend on any LLM provider SDK. CLI invocation only. | AGENTS.md Rule 9 — Banned Patterns. Inherited from REQ-HOOKS-103. |
| C-8 | Policy names SHALL be unique within each domain file and match `[a-z][a-z0-9._-]+`. | Cross-compatibility with AgentCard skill IDs, Veto rule IDs, hooksmith rule names. |
| C-9 | All source files SHALL remain under 512 lines (shell scripts, YAML schemas, static JS plugin). | AGENTS.md Rule 12. |
| C-10 | The policy rendering pipeline SHALL NOT use any Python VM. YAML processing is via `yq` (single-purpose Go binary). Shell scripts SHALL use `grep`, `awk`, `git`, and yq exclusively. | AGENTS.md Rule 5 — Shell-First, Framework-Never. |
| C-11 | `yq` (https://github.com/mikefarah/yq) SHALL be available on PATH. Fallback: `python3 -c "import yaml, json, sys; json.dump(yaml.safe_load(sys.stdin), sys.stdout)"` is an acceptable emergency fallback but SHALL NOT be the primary path. | Shell-first principle. |
| C-12 | Template YAML files SHALL be a working minimal default — seeding from template must produce a valid `policies.json` with zero user edits. | Bootstrap ergonomics. |

## 9. Success Criteria

### Phase 1: Core Policy Engine
- [ ] YAML schema defined and validated for all 24 hook types
- [ ] Template YAMLs seeded to userfiles on first `rules`/`guards` invocation
- [ ] `policy render` merges userfile YAMLs → `policies.json` via yq
- [ ] `policy apply` renders + deploys static plugin JS + policies.json in one command
- [ ] `rules` and `guards` CLIs operational with list/add/delete/update/enable/disable
- [ ] Existing rules (5) and hooks (1) migrated to template→userfile YAML format
- [ ] `policy validate` catches schema and event compatibility errors
- [ ] Run action functional: scripts receive context JSON on stdin, decisions read from stdout, fail-closed on error
- [ ] Userfiles and `policies.json` gitignored; template files tracked
- [ ] All scripts pass shellcheck and remain under 512 lines
- [ ] Extension manifest registers `rules`, `guards`, `policy`, `profile`

### Phase 2: Profiles and Audit
- [ ] `profile save|load|apply|list|delete` operational
- [ ] Built-in profiles: standard, strict, lenient, code-review
- [ ] Audit trail (JSONL hash chain) written by deployed plugin
- [ ] `policy dry-run` simulates policy evaluation against test input
- [ ] Profile inheritance (`extends`) functional

### Phase 3: Advanced Governance
- [ ] Additional domain CLIs: `tool-guards`, `shell-guards`, `system-rules`
- [ ] Agent-scoped policies functional (`agent: "explore"`)
- [ ] Compound conditions (`match_groups` OR-of-ANDs) functional
- [ ] Circuit breaker for A2A remote agent policy violations
- [ ] Policy pack install from git sources

## 10. Glossary of Regulatory Sources (Excerpts)

> **EU AI Act Article 12(1):** "High-risk AI systems shall be designed and developed with capabilities enabling the automatic recording of events (logs) over the lifetime of the system."

> **EU AI Act Article 14(4)(e):** "The oversight measures shall enable [...] the natural person to intervene or interrupt the system through a 'stop' button or similar procedure that brings the system to a halt in a safe state."

> **EU AI Act Article 9(4):** "The risk management measures shall give due consideration to the effects and possible interactions resulting from the combined application of the requirements set out in this Section 2."

> **EU AI Act Article 26(6):** "Deployers shall keep the logs automatically generated by the high-risk AI system for a period of at least six months."

> **EU AI Act Article 50(1):** "AI systems intended to interact directly with natural persons shall be designed and developed in such a way that the natural persons concerned are informed that they are interacting with an AI system."

> **EU AI Act Article 99(2):** "Non-compliance with any of the requirements or obligations under Articles 12 to 26 shall be subject to administrative fines of up to 15,000,000 EUR or, if the offender is a company, up to 3% of its total worldwide annual turnover."

> **GDPR Article 22(1):** "The data subject shall have the right not to be subject to a decision based solely on automated processing, including profiling, which produces legal effects concerning him or her or similarly significantly affects him or her."

> **OWASP LLM06 (Excessive Agency):** "Granting LLMs unrestricted access to backend systems, APIs, and automation tools increases the attack surface. When an LLM can trigger actions autonomously, any prompt injection or model manipulation vulnerability becomes a direct execution primitive with real-world consequences."

> **A2A Protocol §1.2 (Guiding Principles):** "Agents collaborate based on declared capabilities and exchanged information, without needing to share their internal thoughts, plans, or tool implementations."

> **A2A Protocol §7.5 (Authorization):** "A2A Servers must enforce authorization to restrict actions to authorized clients only. Permissions should follow the principle of least privilege."
